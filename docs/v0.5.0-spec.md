# OpenVLCLIP v0.5.0 仕様書

- **Status:** Draft — 実装開始前のレビュー対象
- **Target release:** `openvlclip==0.5.0`
- **Baseline:** `openclip-gemma==0.4.0` / `v0.4.0`
- **Baseline repository:** https://github.com/kotadymo/openclip-gemma
- **Target repository:** https://github.com/kotadymo/openvlclip
- **Target import:** `openvlclip`
- **最終更新:** 2026-10-21

## 1. 目的とスコープ

OpenVLCLIP は **A CLIP-like interface for vision and vision-language foundation models** を掲げる、OpenCLIPに着想を得た**独立した**OSSである。OpenCLIP公式プロジェクト、その公式派生版または完全互換実装を名乗らない。

v0.5.0の目的は、EmbeddingGemma 2専用実装を「今後異なるアーキテクチャのモデルを追加できるライブラリ」へ再編し、名称を `OpenVLCLIP` に変更することである。**v0.5.0に新モデルは追加しない。** 動作可能な実モデルは引き続き `google/embeddinggemma-2` のみとする。

必須成果物：

1. OpenCLIPライクな公開APIの契約の整理と回帰テスト。
2. Model Registry、Backendインターフェース、Capabilitiesの導入。
3. EmbeddingGemma 2固有ロジックのBackendへの分離。
4. 画像・動画検索とインデックスのモデル間互換性設計。
5. 同一GitHubリポジトリのリネーム、Python配布名・import名の変更。
6. 移行ガイド、CI、TestPyPI/PyPIの新プロジェクト公開経路の整備。

v0.6.0で予定する `DINOv2 + dino.txt` を追加する際、公開Factory APIと既存EmbeddingGemma Backendを大幅に変更せず新Backendを追加できる状態を目標とする。`DINOv3 + dino.txt`、`Qwen3-VL-Embedding-2B`、`Jina Embeddings v4 (Dense)` 等は将来候補であり、v0.5.0の実装・サポート表には含めない。

### 1.1 非目標

- DINOv2/dino.txtを含む新モデルの推論実装、Projection学習、独自学習・ファインチューニング。
- Patch Embedding、類似度マップ、Dense Predictionを実際に計算する機能の追加（v0.6.0以降）。
- OpenCLIPの学習API、任意のOpenCLIP重み形式、すべてのFactoryオプションへの完全互換。
- 新しい動画時系列理解、生成型VLM、SAM、MAE、I-JEPA、独自異常検出。
- `openclip-gemma` の既存公開バージョンの削除・上書き。

## 2. 優先順位と互換性原則

実装の判断が衝突する場合、以下の順に優先する。

1. 既存v0.4.0で検証済みのEmbeddingGemma 2数値挙動・安全性・公開API。
2. `docs/v0.4.0-spec.md`、`docs/openclip-compatibility-v0.3.0.md`、`docs/compatibility-spec-v0.1.0.md` の確定契約。
3. 本v0.5.0仕様の名前空間変更・新しいRegistry/Backend/Capabilities契約。
4. OpenCLIP風の呼び出しやすさ。ただし上記に反する動作を無理に模倣しない。

**同じ重み・同じ入力・同じ設定では、v0.4.0とv0.5.0のEmbeddingを対応する精度の既存許容誤差内で一致させる。** 単なる出力shapeの一致を数値互換性とみなさない。

`openclip-gemma` と `openvlclip` は**別のPyPI distribution**である。旧PyPIプロジェクトは残し、公開済みの`openclip-gemma==0.4.0`も利用可能な状態を維持する。旧パッケージを新パッケージへ自動的に置換したり、`openclip-gemma==0.5.0` を公開したりしない。新配布物のimport名は `openvlclip`。旧import名 `openclip_gemma` は新配布物での必須エイリアスとはしない。必要性が確認されるまでは重複実装や移行用shimを追加せず、移行ガイドを提供する。

## 3. リネーム対象

| 対象 | v0.4.0 | v0.5.0 |
| --- | --- | --- |
| 表示名 | openclip-gemma | OpenVLCLIP |
| GitHub | `kotadymo/openclip-gemma` | `kotadymo/openvlclip` |
| PyPI distribution | `openclip-gemma` | `openvlclip` |
| Python import | `openclip_gemma` | `openvlclip` |
| ソースパス | `src/openclip_gemma/` | `src/openvlclip/` |
| インストール | `pip install openclip-gemma` | `pip install openvlclip` |
| リリースタグ | `v0.4.0` | `v0.5.0` |

GitHubは**既存リポジトリのRenameのみ**を行う。新規リポジトリ、Fork、履歴を書き換える移設は行わない。Issue、PR、Star、コミット履歴、既存Releaseを維持し、元リポジトリ名を別のリポジトリで再利用しない。リネーム後に `git remote set-url origin https://github.com/kotadymo/openvlclip.git` を案内する。

`openvlclip` のPyPI名が利用可能であること、必要な商標・名称の調査結果、READMEにおけるOpenCLIPからの独立性の表示が、公開を進める前の**人間による確認ゲート**である。PyPIのPending Trusted Publisher登録だけではプロジェクト名は予約されない。確保できない場合は名称を独断で変更・公開せず作業を停止して報告する。

## 4. 公開Factory API

`openvlclip` のルートから、少なくとも以下をexportする。

- `create_model()`
- `create_model_and_transforms()`
- `create_model_from_pretrained()`
- `get_tokenizer()`
- `list_models()`
- `list_pretrained()`

対応モデル名：`embeddinggemma-2`。v0.4.0同様の大小文字・アンダースコア正規化を維持する。未知名は推測して他Backendへフォールバックせず、対応モデル一覧が分かる `ValueError` を返す。モデル列挙だけでモデル重みの取得・通信を行わない。

### 4.1 Factoryの引数

`create_model` と `create_model_and_transforms` の既存引数を維持する。

- `model_name="embeddinggemma-2"`
- `pretrained="google/embeddinggemma-2"`（`"official"`も受理）
- `precision="fp32"`
- `device="cpu"`（`str` または `torch.device`）
- `cache_dir=None`
- キーワード専用 `output_dict=False`、`logit_scale_mode="strict"`、`modalities=None`

`create_model_from_pretrained` の `pretrained="official"` と `return_transform=True`、戻り値 `(model, preprocess_val)` または `model` を維持する。`create_model_and_transforms` は `(model, preprocess_train, preprocess_val)` の3要素を返す。EmbeddingGemma 2におけるtrain/valの同一決定的前処理を維持する。画像タワーのないtext-only構成で画像Transformを要求した場合は従来どおり明示的に失敗する。

`pretrained=None` は引き続きエラー。サポート外のキーワード・checkpoint・precision・deviceを黙って代替しない。`FP16` と `model.half()` はサポートしない。`FP32` を数値基準とし、`BF16` は既存のCPU/CUDA対応と検証条件を維持する。現行のPythonサポート条件（`>=3.12,<3.15,!=3.14.1`）を維持する。

新たなBackendが必要とする内部オプションはRegistryからBackendに渡し、モデル依存の引数を共通APIへ無制限に増やさない。将来の拡張方法は文書化するが、v0.5.0では任意プラグイン登録の公開APIは必須としない。

### 4.2 Tokenizer

`get_tokenizer(model_name, *, prompt_name=None, context_length=None, cache_dir=None)` の契約を維持する。公式 `SearchQuery` 等のタスクプロンプト、context-length検証、パディング、トークン順序・IDを変更しない。RegistryがTokenizer実装へ委譲するだけで、既存のTransformer tokenizerを独自再実装しない。

### 4.3 list_models/list_pretrained

- `list_models()` は `["embeddinggemma-2"]` を返す。
- `list_pretrained(as_str=False)` は `[("embeddinggemma-2", "official")]` を返す。
- `as_str=True` なら `["embeddinggemma-2:official"]` を返す。
- 返す順序・形状、引数検証、読み込みを行わない性質はv0.4.0準拠とする。

## 5. 公開Model APIと数値契約

Factoryから得るオブジェクトは `torch.nn.Module` 互換であり、既存の `eval()`、`to()`、画像・テキストバッチ入力、デバイス検証を維持する。既存の `EmbeddingGemmaCLIP` 相当の機能を失わせない。内部Adapterのクラス名は実装選択事項だが、旧公開クラスの相当機能・エラーをテストで保護する。

### 5.1 Embedding

- `model.encode_image(image, normalize=False, *, truncate_dim=None)`
- `model.encode_text(text, normalize=False, *, truncate_dim=None)`

両APIはTensorを返す。バッチ次元、入力順序、dtype、device、有限値検証を維持し、`truncate_dim=None` のデフォルトは768。許可する明示次元は `768, 512, 256, 128` のみ。低次元化は先頭成分の切り詰めとL2再正規化である。

**重要：EmbeddingGemma 2の既存出力は`normalize=False`でも公式pooling経路で正規化済みである。`normalize=False`を「生の未正規化特徴量を返す」動作へ変更してはならない。** `normalize=True`は明示的な正規化要求を示すが、EmbeddingGemma 2に対してはv0.4.0の出力契約を変えない。将来別Backendに適用する際はCapabilities/Backend仕様でそのモデルの正規化意味を明示し、未定義の動作を暗黙に揃えない。

### 5.2 forward/get_logits

- `model.forward(...)` と `model.get_logits(...)` は、EmbeddingGemma 2でデフォルト `logit_scale_mode="strict"` のまま呼ぶと `NotImplementedError`。
- `logit_scale_mode="cosine"` を明示したときのみ利用可能。
- `forward()` の返値はv0.4.0と同じ3要素 `(image_features, text_features, logit_scale)`、または `output_dict=True` 時の同等dict。
- `get_logits(image, text)` は `(image_logits, text_logits)` の2行列。`image_logits` は正規化済み画像・テキスト特徴量の内積、`text_logits` はその転置。
- 返す `logit_scale` は**学習済みCLIPスケールではなく値1.0の非学習済み乗算係数**。未較正のcosine scoreを分類確率や学習済みlogitsと呼ばない。
- v0.4.0の `truncate_dim`、片側のみ入力時の処理、出力形式、エラー順序、dtype/device、非finite値拒否を維持する。

### 5.3 選択的ロードとMRL

`modalities=None` は現行のfull-load経路。`("text",)` はtext-only、`("text", "image")` は画像＋テキストの選択的ロード。重複・未対応・image-onlyなどを拒否する。既存の pinned Transformers設定を使い、ロード後にレイヤーを削除する実装へ変更しない。保持したモダリティの埋め込みはfull-loadと精度別許容誤差で一致し、存在しないimage encoderを呼ぶと明示エラーを返す。

## 6. Model Registry

`src/openvlclip/registry.py` に、モデル名をBackendとモデル記述子へ解決する読み取り中心のRegistryを設ける。

モデル記述子には最低限、次を含める。

- 正式な `model_name` と許可する名前エイリアス
- `backend_id`
- default checkpointの `model_id` と固定 `revision`
- 公開 `pretrained` タグと実際のcheckpointの対応
- Capabilities
- 対応するTokenizer/Preprocess factory
- Embedding空間の識別に必要なBackend固有設定の取得口

v0.5.0で登録するエントリは `embeddinggemma-2` **1件のみ**。モデルの登録・一覧取得では実モデルのロード、ネットワークアクセス、GPU初期化を行わない。未知名、重複エントリ、矛盾したpretrained tag、未登録Backendは明確に失敗する。

**追加モデルの受け入れテスト**として、テスト専用の軽量Fake BackendをRegistryに差し込んでFactory委譲を確認してよい。ただしFakeモデルを `list_models()` に公開したり、実モデルとして配布したりしない。v0.6.0でDINOv2 Backendを追加しても、一般のFactory分岐に `if model_name == ...` を追加し続ける構造を避ける。

## 7. Backend設計

想定構成（構造は最小限必要な範囲で変更可）：

```text
src/openvlclip/
    __init__.py
    factory.py
    registry.py
    capabilities.py
    backends/
        __init__.py
        base.py
        embeddinggemma2.py
    model.py
    tokenizer.py
    transforms.py
    batching.py
    image_search.py
    video_search.py
    index_storage.py
    ...
```

共通FactoryはRegistryの解決と引数の共通検証を行い、Backendへロード・Tokenizer・Transform構築を委譲する。`backends/base.py` には必要最小限の `Protocol` / 抽象インターフェースを置く。

Backendの責務：

1. checkpoint/config/processor/tokenizerの取得とrevision固定。
2. model固有の画像前処理・テキストプロンプト・pooling・正規化・切り詰め・スコア処理。
3. モダリティ選択・モデル固有のprecision制限と未対応操作の明示。
4. 埋め込み空間の互換性を判定するためのメタデータ提供。

共通層の責務：

1. Registry解決、公開Factoryの戻り値・基本的なバッチ順序。
2. 共通の画像・動画検索ワークフローと安全なインデックス入出力。
3. 対応Capabilitiesの問い合わせと明示的な失敗。
4. 共有可能なテスト・CLI・README例。

v0.4.0のTransformerモデル・pooling・前処理・索引ロジックを**不要に全面書き換えない**。Adapterと委譲を優先し、モデル重みを読み込む実装を重複させない。

## 8. Capabilitiesの公開契約

`model.capabilities` を読み取り専用の `Mapping[str, bool]` として提供する。必須キー：

| Key | EmbeddingGemma 2 (v0.5.0) | 意味 |
| --- | --- | --- |
| `image_embedding` | `True` | `encode_image` |
| `text_embedding` | `True` | `encode_text` |
| `image_text_similarity` | `True` | 明示的なcosineモードで画像・テキスト比較 |
| `patch_embedding` | `False` | `encode_patches` に対応 |
| `text_similarity_map` | `False` | `similarity_map` に対応 |
| `mrl` | `True` | 768/512/256/128の公式方式 |
| `selective_loading` | `True` | `modalities` でtowerを選択 |

CapabilitiesはRegistryメタデータと生成済みモデルで一致すること。ただし `modalities=("text",)` 等、インスタンス固有の構成では実際に使える操作を正確に反映するか、別のインスタンス情報で利用不可を明示する。**text-onlyモデルが画像Embedding可能だと誤表示してはならない。**

未対応の `encode_patches()` / `similarity_map()` をv0.5.0で共通APIとして公開する場合は、`NotImplementedError` と対応Backend/Capability名を示す。未実装なのに空Tensor・ダミーマップ・不正確な近似を返さない。将来のv0.6.0で形状・戻り値を確定するため、v0.5.0で過剰な仕様を固定しない。

## 9. 画像・動画検索とインデックス互換性

### 9.1 保存・読み込みの維持

v0.4.0の以下を新import名の下で引き続き提供する。

- `iter_image_embeddings()`（公開引数は `embedding_dim`）
- `build_or_update_image_index()` / `search_images()` / `convert_image_index()`
- `build_or_update_video_index()` / `search_video()` / `convert_video_index()`
- 保存済みインデックスの安全な読み込み、原子的書き込み、入力検証、checksum、pickle禁止、アーカイブサイズ・NPYヘッダ事前検査
- 768/512/256/128次元、既存CLI、テキスト`SearchQuery`プロンプトの検索挙動

v0.4.0の画像形式v2・動画形式v3と、旧画像v1・動画v2の対応範囲を維持する。古い動画v1を新たに読めると約束しない。既存インデックスを新パッケージで無再生成に読み込めることを実ファイルテストで確認する。

### 9.2 異なるEmbedding空間の混合禁止

**Embedding次元数が一致するだけでは比較可能としない。** 新規索引メタデータとロード時の互換性判定では、最低限次を扱う。

- `backend_id`、正式 `model_id`、checkpoint `model_revision`
- `embedding_dimension`、`embedding_strategy`、`normalization`
- `preprocessing_id`（画像前処理と、動画ならsampling仕様）
- インデックス生成時のタスクプロンプトと、検索時のqueryプロンプト方針（該当しない値は明示的に区別）
- `model_precision`、保存dtype、既存checksum・フォーマットバージョン
- 将来の異種モデル判定に使う`embedding_space_id`相当の、安定かつ決定的な署名

文字列署名を構築する場合は、対象フィールドの固定順序と正規化規則を文書化し、Pythonのランダムハッシュ値や環境依存の識別子を使わない。互換条件を満たさない更新、変換、画像・テキスト比較を明示的に拒否する。未対応Backendの推論・インデックス自動変換は実施しない。

**後方互換性**：v0.4.0の索引にはこれら新規項目が存在しないため、既知の旧形式についてのみ、既存の `model_id` / pinned revision / preprocessing / embedding strategy / dimension等から安全に推定可能な既定値を適用する。未知モデルや未知revisionに対して不足情報を都合よく推定しない。

デフォルトでは画像v2・動画v3の保存形式を維持し、既存の必須項目・検証を弱めず後方互換な拡張を検討する。**必須フィールドの追加によって既存同一version形式が読めなくなる場合**は、そのままv2/v3の意味を破壊せず、明示した新format versionと移行テストを設計してPRで根拠を示す。フォーマットversionの変更は自動的な目的ではない。

v0.5.0の登録BackendはEmbeddingGemma 2だけでも、Fake Backendと偽メタデータによって「次元一致・モデル不一致」「revision不一致」「正規化方式不一致」「prompt不一致」を回帰テストする。

## 10. 旧パッケージからの移行

新しい配布名・import名・Repository URLの変更を、`docs/migration-v0.5.0.md` とREADMEに記載する。

**従来：**

```python
from openclip_gemma import create_model_and_transforms, get_tokenizer

model, _, preprocess = create_model_and_transforms("embeddinggemma-2")
tokenizer = get_tokenizer("embeddinggemma-2")
```

**v0.5.0：**

```python
from openvlclip import create_model_and_transforms, get_tokenizer

model, _, preprocess = create_model_and_transforms("embeddinggemma-2")
tokenizer = get_tokenizer("embeddinggemma-2")
```

インストール例：

```bash
pip install openvlclip
# 動画機能が必要な場合
pip install "openvlclip[video]"
```

`openclip-gemma` の自動アンインストールは行わない。同一環境で両distributionが導入される場合の独立したimportと依存関係を検証するか、未検証の共存を保証しない旨を明記する。旧distributionのPyPI表示、既存バージョン、リリースタグは変更・削除しない。

README、`pyproject.toml`（name/version/description/keywords/URLs）、`uv.lock`、examples、tests、CLI、workflow、徽章・リンク、`LICENSE`等のパス・名前表記を点検する。`EmbeddingGemmaCLIP`のような歴史的型名は、リネームを理由に数値動作を壊さない限り残してよい。

## 11. 実装フェーズとPR分割

### Phase A — 公開API仕様と互換性テスト

ブランチ案：`feature/v0.5.0-api`

- 旧公開API、normalize、strict/cosine、precision、device、selective loadingの契約を固定する。
- v0.4.0実モデルとの数値比較の基準データ／対照テストを用意する。
- OpenCLIPとの互換部分と意図的な非互換部分をドキュメント化する。
- 数値契約に理由のない変更を加えない。

### Phase B — Registry/Backend/Capabilities

ブランチ案：`feature/v0.5.0-backends`

- Model Registry、Backendプロトコル、Capabilitiesを実装する。
- EmbeddingGemma 2固有ローダー・Tokenizer・PreprocessをBackendへ委譲する。
- 検索とインデックスのfeature-space互換チェックを追加し、旧索引を維持する。
- Mock/Fake Backendと既存モデルによるFactory・例外・数値の回帰テストを追加する。

### Phase C — 新名称とパッケージの準備

ブランチ案：`feature/v0.5.0-rename`

- `src/openvlclip/` へ移行し、distribution名を `openvlclip` に変更する。
- 全import、CLI、文書、テスト、ワークフロー、lockfileを更新する。
- 新名前空間のクリーンなwheel/sdist installと既存索引の読み込みを確認する。
- Renameの人間ゲートと公開設定が整うまでは、GitHubリポジトリ名変更・PyPI公開を**独断で実施しない**。

フェーズごとにmain向けPRでレビュー・CIを実施する。通常は`main`基点とし、不要な`develop`ブランチを新設しない。最終的な実リポジトリRenameは、コード・CIの準備ができ、PyPI名・商標・移行手順の確認後に実施する。Rename後にRepository URL、Remote、GitHub Actions、OIDC Trusted Publisherを再確認する。

## 12. テスト仕様と検証マトリクス

### 12.1 軽量テスト（必須・通常CI）

- Registryのモデル一覧、未知名、重複、pretrained tag、例外、Fake Backendへの委譲。
- Capabilitiesの必須キー、型、モデル/インスタンス整合性、unsupported featureの明示的エラー。
- Factoryのdefault/positional/keyword引数・戻り値・エラー、text-only時のTransform拒否。
- `normalize=False/True`、MRL全4次元、L2 norm、strict/cosine、output_dict、logitsの転置一致。
- batch order、streaming、画像・動画索引作成/更新/読み込み/検索/変換、CLI・READMEの例。
- 旧画像v1/v2、動画v2/v3、チェックサムと安全な読み込み、破損データ、異なる次元・モデル・revision・promptの拒否。
- wheel/sdistのパッケージ名、`src/openvlclip`の取り込み、旧 `openclip_gemma` へのハードコード参照の検出。
- importや`list_models()`がモデル重みをダウンロードしないこと。

### 12.2 実モデル統合テスト（CPU/CUDA、実行条件記録）

- v0.4.0とv0.5.0で同一の固定revision・画像・テキスト・prompt・前処理を用いる比較。
- `768/512/256/128`、FP32/BF16、full/text-only/text+imageの保持モダリティ。
- shape、dtype、device、finite、unit norm、最大絶対誤差とcosineを記録し、既存の精度別許容差を用いる。
- 既存のSentence Transformers公式経路との比較も維持する。
- PyAV optional依存がある/ない両状態のインストール・動画機能テスト。
- Windows/Linux・Python 3.12/3.13/3.14（3.14.1除外）の通常CIを維持する。CUDAや重量級実モデルテストは実行環境がないとき`skipped / unverified`と明記し、合格と偽らない。

### 12.3 公開アーティファクト検証

- `uv lock --check`、pytest、Ruff、wheel/sdistの構築・内容検証。
- ソースツリー外の新規仮想環境で、PyPI/TestPyPIから取得した**実配布wheel**のimport/モデル推論/検索。
- メタデータの`Name=openvlclip`、`Version=0.5.0[rcN]`、新GitHub URL、Extrasを検証。
- v0.4.0旧索引ファイルを新配布物で読み、同じ検索結果・安全性が維持されること。
- 代表的な実データがない場合、合成テストの通過を検索品質向上の根拠にしない。

## 13. GitHubリポジトリRenameと公開ゲート

以下は**ユーザー承認を必要とする運用変更**であり、仕様作成や通常コードPRの一部として勝手に実行しない。

1. `openvlclip` のPyPI名の使用可能性・名称/商標調査を確認する。利用不可ならリリースを停止する。
2. `kotadymo/openclip-gemma` の既存リポジトリを `kotadymo/openvlclip` へRenameする。履歴・Issues・Starsを保持し、clone元と文書URLを更新する。
3. リポジトリRename後、GitHub Actionsのpermissions、Environment `testpypi`/`pypi`、tag許可、Required reviewersとOIDC claimを確認する。
4. **新PyPIプロジェクト `openvlclip` 用のTrusted Publisherを別途設定**する。旧`openclip-gemma`プロジェクトのTrusted Publisher設定をそのまま新プロジェクトの認証として利用できると仮定しない。
5. 旧`openclip-gemma`プロジェクトのTrusted PublisherはリポジトリRenameによる名前不一致を見直し、古い公開パスの意図しない利用を防ぐ。旧パッケージの既存配布物は維持する。
6. v0.5.0用の新しいversion/tag限定Workflowを設け、CI成功のmain commitにのみ `v0.5.0rc1` と `v0.5.0` を付ける。既存タグを削除・再利用しない。
7. `TestPyPI openvlclip==0.5.0rc1` の公開、クリーンインストール、実モデル回帰検証を先に行う。
8. Environment承認を経て `PyPI openvlclip==0.5.0` を正式公開し、PyPI配布物の検証後にGitHub Releaseを作成する。

推奨ワークフローのファイル名（実装時に厳密な命名と登録を一致させる）：

- `.github/workflows/publish-testpypi-v0.5.0rc1.yml` — `testpypi`
- `.github/workflows/publish-pypi-v0.5.0.yml` — `pypi`

GitHub側のタグ保護/Environment承認と、PyPI側のRepository owner/name・Workflow filename・Environmentを一致させる。OIDCの`id-token: write`をpublish jobに限定し、通常CIに公開権限を与えない。古いv0.4.0ワークフローを新distributionのタグで誤起動させない。

## 15. Copilot実装時の指示

本ドキュメントは**実装仕様**であり、仕様作成時点ではRenameや公開を承認しない。各Phase開始時に影響範囲、API契約、後方互換性、テスト計画を説明する。仕様とv0.4.0の確定挙動が矛盾すると判明した場合は、実測と公式資料を示して相談し、黙って仕様または数値動作を変えない。

v0.5.0では**新モデル追加を行わず**、必要な最低限の設計のみ実装する。PRをPhaseごとに分け、公開は最終ゲート通過後に行う。失敗したCIや未検証のGPU/OSを成功と報告せず、GitHubとPyPIの保護設定は回避しない。
