# v0.8.0 exact image/video search optimization

**Development scope:** Improve candidate selection in the existing NumPy exact-search engine. No FAISS dependency, ANN index, or persistent format change is introduced by this PR.

Previously, image/frame searches created Python score-row tuples for *all* 4096 scores in each block, then merged and sorted the whole candidate set. Native-video search sorted all scores in Python. The shared `select_top_k` helper now uses NumPy `partition` to identify the block-level top-k cutoff, materializing only candidates meeting that score cutoff, then applies the original secondary ordering.

**Tie semantics:** All rows tied at the cutoff are retained before applying the original secondary/path ordering, so the exact score, index, and tie priority are maintained. High-tie workloads may still process many candidates; this is intentional for correctness.

**Compatibility:** Index archives, model EmbeddingSpace settings, scores and public function signatures remain unchanged. The NumPy path remains the default and needs no extra dependency.

## Measurement (2026-10-23)

`benchmarks/benchmark_exact_search.py` compares the previous full-sort behavior with `select_top_k`. It times top-k selection on precomputed scores, 4096-row block image queries, and single-pass native-video-style queries including the matrix-vector score calculation. Each case uses two warmups and five timed runs; values are medians. The table reports the median of nine per-case speedup ratios (three dimensions × three `k` values), followed by their min–max range. Speedup is old latency divided by new latency.

| Vectors | Ties | Top-k only | Block image query | Single-pass query |
| ---: | --- | ---: | ---: | ---: |
| 1,000 | Low | 29.79× (6.71–38.69) | 3.25× (2.58–3.54) | 3.26× (2.66–3.63) |
| 10,000 | Low | 144.80× (71.34–184.12) | 6.68× (5.55–10.55) | 15.83× (6.49–22.70) |
| 100,000 | Low | 423.36× (376.31–497.27) | 4.70× (3.39–5.93) | 13.96× (9.80–19.14) |
| 1,000 | All scores equal | 0.68× (0.64–0.80) | 0.74× (0.66–0.89) | 0.83× (0.60–0.88) |
| 10,000 | All scores equal | 0.66× (0.61–0.78) | 0.86× (0.80–0.94) | 0.83× (0.73–0.96) |
| 100,000 | All scores equal | 0.77× (0.75–0.81) | 0.82× (0.77–0.85) | 0.83× (0.77–0.84) |

The full matrix covered 1k/10k/100k rows, dimensions 512/768/1152, `k=5/10/100`, and low-tie random unit vectors or an intentionally pathological all-equal-score workload: 54 cases total. Full ordering and scores matched the pre-optimization reference in all 54 cases. Low-tie workloads were faster. The all-equal case is slower because every candidate must still be sorted to preserve the exact secondary order, while partition adds overhead; this confirms there is no universal speedup claim. Peak memory was not measured.

Reproduce with:

```powershell
.\.venv\Scripts\python.exe benchmarks\benchmark_exact_search.py --output $env:TEMP\openvlclip-v080-search.json
```

The run used Windows 11, Python 3.12.10, NumPy 2.5.4, and an Intel Core i7-14700F. Full environment and validation details are in the [v0.8.0 validation record](v0.8.0-validation.md).
