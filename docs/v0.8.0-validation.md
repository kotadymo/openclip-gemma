## PE-Core configuration and optional API

Both immutable timm snapshots loaded through
`open_clip.create_model_and_transforms("local-dir:<snapshot>")` and
`open_clip.get_tokenizer("local-dir:<snapshot>")` with open-clip-torch 3.3.0.
The snapshots specify 384×384 input, 512-dimensional global features,
32-token context, bilinear interpolation, squash resize, and mean/std
`[0.5, 0.5, 0.5]`. The existing preprocessing identity
`pecore-rgb384-bilinear-squash-normalize-0.5-v1` matches this configuration;
the loader now rejects a pinned config that diverges from these fields. The
identity and index format were not changed.

The tests also verified the model registry can be imported and listed without
the optional `open_clip` module, and that model/tokenizer creation reports the
`[pecore]` installation instructions when the dependency is absent.

## Pinned-checkpoint CPU FP32 parity

The reference and OpenVLCLIP models were instantiated separately from the
same pinned official checkpoints. SigLIP 2 used
`transformers.AutoModel`/`AutoProcessor`; PE-Core used the same timm-converted
snapshots through an independent OpenCLIP 3.3.0 model and tokenizer. PE-Core
results therefore establish parity to the converted OpenCLIP checkpoint, not
to Meta's separately packaged original weights or implementation.

All tests used CPU FP32 and `rtol=atol=1e-5`. Processor tensors and token IDs
were required to match exactly. The deterministic inputs were two solid-color
non-square RGB images and two text prompts per checkpoint. Every listed
maximum absolute error was `0.0`.

SigLIP 2 logits were compared against the official model's image/text logits,

## SigLIP 2 CUDA FP32/BF16 parity

Each CUDA case was run as an individual pytest process against the pinned
official checkpoint to limit retained GPU memory. All completed cases
reported `0.0` maximum absolute error for raw and normalized image/text
features and logits. The test tolerances were `1e-5` for FP32 and `2e-3` for
BF16.

| Model | CUDA FP32 | CUDA BF16 |
| --- | --- | --- |
| `siglip2-base` | PASS | PASS |
| `siglip2-naflex-base` | PASS | PASS |
| `siglip2-base-384` | PASS | PASS |
| `siglip2-large-256` | NOT COMPLETED | PASS |
| `siglip2-so400m-384` | PASS | PASS |

The `siglip2-large-256` FP32 case was stopped after 600 seconds to protect
the shared GPU. At the time, `nvidia-smi` showed 15,835 MiB of 16,376 MiB in
use, 541 MiB free, and 100% utilization. Both model copies had loaded, but
the test had not produced parity output. This case is **UNVERIFIED**, not a
numerical failure. The other four FP32 cases and all five BF16 cases passed.

Transformers emitted a configuration warning that BOS/EOS IDs 49406/49407
are outside the configured vocabulary size 32000 for these SigLIP checkpoints.
Despite that upstream warning, the independently loaded reference and wrapper
produced exactly matching processor tensors, token IDs, features, and logits
for the tested inputs. Windows Hugging Face cache symlink warnings also
appeared; those affect cache space efficiency, not the numerical checks.

## Exact-search performance and ranking

`benchmarks/benchmark_exact_search.py` compares the previous full-sort
reference with the partition-based selector. It measures precomputed-score
top-k, 4096-row chunked image-query latency, and single-pass
native-video-style query latency including matrix-vector scoring. Rows and
queries are deterministic FP32 unit vectors for low ties; the high-tie case
sets every vector and query to the same unit vector. The parameter matrix is
3 sizes × 3 dimensions × 3 `k` values × 2 tie modes = 54 cases. Each case has
two warmups and five timed runs; each latency is the median, and the table
reports the median speedup ratio across the nine dimension/`k` combinations
per size/tie group (with the observed range).

| Vectors | Tie workload | Top-k only | Chunked image query | Single-pass query |
| ---: | --- | ---: | ---: | ---: |
| 1,000 | Low | 29.79× (6.71–38.69) | 3.25× (2.58–3.54) | 3.26× (2.66–3.63) |
| 10,000 | Low | 144.80× (71.34–184.12) | 6.68× (5.55–10.55) | 15.83× (6.49–22.70) |
| 100,000 | Low | 423.36× (376.31–497.27) | 4.70× (3.39–5.93) | 13.96× (9.80–19.14) |
| 1,000 | All scores equal | 0.68× (0.64–0.80) | 0.74× (0.66–0.89) | 0.83× (0.60–0.88) |
| 10,000 | All scores equal | 0.66× (0.61–0.78) | 0.86× (0.80–0.94) | 0.83× (0.73–0.96) |
| 100,000 | All scores equal | 0.77× (0.75–0.81) | 0.82× (0.77–0.85) | 0.83× (0.77–0.84) |

Old and new result order and scores matched in **54/54 cases**. Low-tie cases
were faster. The synthetic all-equal case is slower because exact tie ordering
requires processing every candidate and `partition` adds overhead; this is a
worst-case result, and no universal speedup is claimed. Peak memory was not
measured.

Reproduce the full matrix with:

```powershell
.\.venv\Scripts\python.exe benchmarks\benchmark_exact_search.py `
  --output $env:TEMP\openvlclip-v080-search.json
```
