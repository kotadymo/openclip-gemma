## Phase 0 findings

- The four HF repositories and immutable revisions, source hashes, model-file hashes, and license findings are recorded in [model provenance](./model-provenance-v0.7.0.md). The downloaded SigLIP, Qwen 2B, and Qwen 8B weight files were locally SHA-256 checked against the pinned HF LFS digests.
- SigLIP 2 FixRes and NaFlex both loaded on CUDA in FP32 and BF16. FP32 outputs were 768-dimensional and the learned scale/bias logits matched the official formula within `9.54e-7` (FixRes) and `0.0` (NaFlex). Measured BF16-vs-FP32 feature and logit deltas are recorded in the provenance document; these were single synthetic-input precision probes, not benchmarks.
- The pinned Qwen 2B wrapper loaded in CUDA FP32 and BF16. Text-only, image-only, and mixed text-image inputs returned finite `(3, 2048)` outputs; BF16-vs-FP32 maximum absolute difference was `0.00418`. Two-frame video-only and text-video inputs returned finite `(2, 2048)` BF16 outputs.
- The Qwen MRL contract is determined by spec §7.3 and §19.1 item 4: allow dimensions in the model-card range (64 through native), truncate the unnormalized pooled feature, then L2-normalize. The pinned wrapper does not expose `truncate_dim`; Sentence Transformers 5.4.0 confirms the truncation-then-normalization mechanics at dimensions 64, 257, 1024, and the native dimension, but its default text path prepends the instruction to plain text (11 tokens) rather than using the wrapper's system/user/assistant-generation chat template (25 tokens). Same-text BF16 embeddings differed by up to `0.05670`; treat the two routes as separate embedding strategies, not as interchangeable vectors or indexes.
- The independent Qwen 8B wrapper comparison against a separately loaded official Transformers reference passed on CPU FP32 and BF16, with max absolute error `0.0` for global features and tested MRL dimensions 64, 257, 1024, and native. CUDA remains unverified. See the [Phase 3 parity record](./model-provenance-v0.7.0.md#phase-3-qwen3-vl-embedding-wrapper-parity).
- The Qwen 8B tokenizer-only compatibility probe found that the official processor path produced `(2, 30)` token IDs while direct `tokenizer.apply_chat_template(..., tokenize=True)` produced `(2, 29)`. The official processor marks a valid final token with the same ID as its pad token (`151643`), so a bare token tensor cannot reconstruct the official attention mask. Use processor-aware `encode_texts`; the legacy `get_tokenizer` → `encode_text` route must remain unsupported unless exact parity is later demonstrated.
- The pinned Qwen source uses `trust_remote_code=True` and converts vision-processing exceptions to a `"NULL"` input. Tests used the audited source file and fixed local checkpoint; OpenVLCLIP must not adopt unpinned remote code or silently produce NULL embeddings.
- The project lock resolves Torch 2.14.1, Torchvision 0.29.1, and Transformers 5.20.1. Qwen 2B and both SigLIP checkpoints ran in an isolated Windows Python 3.12 CUDA environment with Torch `2.14.1+cu130`; Qwen 8B CPU FP32/BF16 parity used the CPU device in the same environment. The Windows/Linux/Python CI matrix is recorded under the corresponding PRs.

## Qwen 8B GPU gate interpretation

The wording in spec §§12.2, 16, and 19.1 requires official Qwen 8B parity on **at least one validated high-memory GPU configuration**, establishes FP32 as the numerical baseline, and requires a separate BF16 tolerance. It does not explicitly require both FP32 and BF16 to be run on CUDA. The existing independent CPU FP32 parity supplies the FP32 baseline. Accordingly, one successful independent CUDA BF16 parity run on a suitable GPU, with its device, precision-specific tolerance, and memory measurements recorded, is planned to satisfy the written GPU minimum; CUDA FP32 will remain clearly marked **not evaluated** unless it is also run. This is an interpretation of the current text, not a specification change or a claim that the GPU gate has passed. The full official input/MRL cases still need to pass on that GPU. If the project intends both GPU dtypes to be mandatory, the normative specification must be explicitly amended rather than inferred from progress notes.

## Blocking GPU requirement

The system Python 3.12.10 still has CPU-only Torch `2.14.0+cpu`. The isolated CUDA environment has CUDA 13.0, Torch `2.14.1+cu130`, Transformers `5.20.1`, and BF16 support on an NVIDIA RTX 4070 Ti SUPER with 16,376 MiB total and approximately 14,309 MiB free at the latest GPU query. The separate isolated CPU environment uses Torch `2.14.0+cpu`, Transformers `5.20.1`, and `qwen-vl-utils==0.0.14`.

The pinned Qwen 8B checkpoint contains 8,144,793,840 BF16 parameters in four shards totaling 16,289,679,624 bytes (15.17 GiB). All shards were downloaded outside the repository and their SHA-256 digests match the pinned HF LFS metadata. The weights alone exceed currently free VRAM, leaving no room for inference activations or buffers. The repository has no configured self-hosted Actions runners. The available RTX 4070 Ti SUPER currently reports 16,376 MiB total and 14,374 MiB free; 8B CUDA parity remains unavailable here.

**Remaining Phase 0 gate:** provide access to a CUDA-enabled high-memory GPU host with enough free VRAM for the full BF16 checkpoint and runtime buffers. A 24 GiB-or-larger device is a practical starting point, not a measured minimum. Verify the environment with:

```powershell
nvidia-smi --query-gpu=name,memory.total,memory.free --format=csv
python -c "import torch; print(torch.__version__, torch.cuda.is_available(), torch.version.cuda)"
```

Do not substitute quantization or unverified CPU offload. Once a suitable GPU is available, run the independent Qwen 8B parity matrix in CUDA BF16 (and CUDA FP32 if resources permit) with the fixed revision, and record peak VRAM. See the [parity test](../tests/integration/test_qwen3vl_official_parity.py) for the invocation and case selection. The official processor's video path also emitted a `cap_pixels_per_frame` warning in the CPU probe, so arbitrary video pixel-budget parity remains unverified. Safe backend implementation can proceed, but do not claim the 8B GPU gate passed or v0.7.0 release-ready until the required GPU cases pass.
