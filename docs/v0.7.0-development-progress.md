## Phase 0 findings

- The four HF repositories and immutable revisions, source hashes, model-file hashes, and license findings are recorded in [model provenance](./model-provenance-v0.7.0.md). The downloaded SigLIP, Qwen 2B, and Qwen 8B weight files were locally SHA-256 checked against the pinned HF LFS digests.
- SigLIP 2 FixRes and NaFlex both loaded on CUDA in FP32 and BF16. FP32 outputs were 768-dimensional and the learned scale/bias logits matched the official formula within `9.54e-7` (FixRes) and `0.0` (NaFlex). Measured BF16-vs-FP32 feature and logit deltas are recorded in the provenance document; these were single synthetic-input precision probes, not benchmarks.
- The pinned Qwen 2B wrapper loaded in CUDA FP32 and BF16. Text-only, image-only, and mixed text-image inputs returned finite `(3, 2048)` outputs; BF16-vs-FP32 maximum absolute difference was `0.00418`. Two-frame video-only and text-video inputs returned finite `(2, 2048)` BF16 outputs.
- The Qwen MRL contract is determined by spec §7.3 and §19.1 item 4: allow dimensions in the model-card range (64 through native), truncate the unnormalized pooled feature, then L2-normalize. The pinned wrapper does not expose `truncate_dim`; Sentence Transformers 5.4.0 confirms the truncation-then-normalization mechanics at dimensions 64, 257, 1024, and the native dimension, but its default text path prepends the instruction to plain text (11 tokens) rather than using the wrapper's system/user/assistant-generation chat template (25 tokens). Same-text BF16 embeddings differed by up to `0.05670`; treat the two routes as separate embedding strategies, not as interchangeable vectors or indexes.
- A pinned Qwen 8B CPU FP32 run returned finite `(1, 4096)` vectors for text, image, text-image, two-frame video, and text-video inputs. Manual truncate-then-normalize checks returned unit-norm vectors at dimensions 64, 257, 1024, and 4096. These checks establish execution and post-processing shape/norm only, not OpenVLCLIP parity or CUDA support.
- The Qwen 8B tokenizer-only compatibility probe found that the official processor path produced `(2, 30)` token IDs while direct `tokenizer.apply_chat_template(..., tokenize=True)` produced `(2, 29)`. The official processor marks a valid final token with the same ID as its pad token (`151643`), so a bare token tensor cannot reconstruct the official attention mask. Use processor-aware `encode_texts`; the legacy `get_tokenizer` → `encode_text` route must remain unsupported unless exact parity is later demonstrated.
- The pinned Qwen source uses `trust_remote_code=True` and converts vision-processing exceptions to a `"NULL"` input. Tests used the audited source file and fixed local checkpoint; OpenVLCLIP must not adopt unpinned remote code or silently produce NULL embeddings.
- The project lock resolves Torch 2.14.1, Torchvision 0.29.1, and Transformers 5.20.1. Qwen 2B and both SigLIP checkpoints ran in an isolated Windows Python 3.12 CUDA environment with Torch `2.14.1+cu130`; Qwen 8B ran in a separate Windows Python 3.12 CPU environment with Torch `2.14.0+cpu`, Transformers `5.20.1`, and `qwen-vl-utils==0.0.14`. CPU BF16 and the Windows/Linux/Python matrix remain unverified. No project dependency or lockfile was changed.

## Phase 1 implementation (merged)

- `backends.base` defines processor-aware image, multimodal, and video input types. EmbeddingGemma and dino.txt retain their tensor-only image paths; they reject processor mappings explicitly.
- Both existing model wrappers expose `encode_texts()` for plain text. EmbeddingGemma reuses the model's configured cache directory when creating its tokenizer. Unsupported task instructions, `encode_multimodal()`, and `encode_video()` remain explicit errors rather than fallback embeddings.
- Capabilities include `video_embedding`, `multimodal_embedding`, `instruction_aware`, `variable_resolution`, and `sigmoid_logits`; modality filtering disables features that cannot operate on the loaded modality set.
- Phase 1 did not change `EmbeddingSpace` signatures or index serialization. Its Windows Python 3.12.10 snapshot was **323 passed, 30 skipped**; that run predates Phase 2 and is not the current full-suite result.
- PR [#42](https://github.com/kotadymo/openvlclip/pull/42) merged at `51cce1f3dfc0f3a276e68dbfa0569341e59222e6`; its post-merge main CI passed in [run 39817058942](https://github.com/kotadymo/openvlclip/actions/runs/39817058942).

## Phase 2 implementation (in progress)

- Added the pinned FixRes and NaFlex backends, registry entries, 768-dimensional features, fixed-length tokenizer, strict learned scale/bias logits, cosine mode, and explicit rejection of unsupported MRL, prompts, selective loading, and patch/map operations.
- NaFlex preprocessing preserves `pixel_values`, `pixel_attention_mask`, and `spatial_shapes` through shared image batching and image-index search. The fixed `max_num_patches` limit is validated.
- Focused unit/regression tests for SigLIP 2, batching, registry, Factory, dino.txt, and model API: **151 passed, 4 skipped**.
- The official parity integration compared both pinned checkpoints against separate official Transformers model/processor instances: **6 passed** across CPU FP32 and CUDA FP32/BF16. Token IDs and processed image fields matched exactly; image/text features and scaled logits had observed maximum absolute error `0.0` for the tested inputs. CPU FP32 image-index build/search passed for both variants. See the detailed [model provenance results](./model-provenance-v0.7.0.md).
- The Windows Python 3.12.10 full suite passed: **337 passed, 36 skipped** (three non-fatal xFormers-unavailable warnings from the dino.txt integration). Ruff check/format, `uv lock --check`, and Pylance diagnostics passed for the changed Python files.
- The parity run used synthetic images and text and is not a retrieval-quality benchmark. CPU BF16, the Windows/Linux and Python-version CI matrix, PR/CI/review, and merge remain pending.

## Blocking GPU requirement

The system Python 3.12.10 still has CPU-only Torch `2.14.0+cpu`. The isolated CUDA environment has CUDA 13.0, Torch `2.14.1+cu130`, Transformers `5.20.1`, and BF16 support on an NVIDIA RTX 4070 Ti SUPER with 16,376 MiB total and approximately 14,309 MiB free at the latest GPU query. The separate isolated CPU environment uses Torch `2.14.0+cpu`, Transformers `5.20.1`, and `qwen-vl-utils==0.0.14`.

The pinned Qwen 8B checkpoint contains 8,144,793,840 BF16 parameters in four shards totaling 16,289,679,624 bytes (15.17 GiB). All shards were downloaded outside the repository and their SHA-256 digests match the pinned HF LFS metadata. The weights alone exceed currently free VRAM, leaving no room for inference activations or buffers. The repository has no configured self-hosted Actions runners. Therefore the mandatory Qwen 8B GPU parity gate cannot be completed here.

**Remaining Phase 0 gate:** provide access to a CUDA-enabled high-memory GPU host with enough free VRAM for the full BF16 checkpoint and runtime buffers. A 24 GiB-or-larger device is a practical starting point, not a measured minimum. Verify the environment with:

```powershell
nvidia-smi --query-gpu=name,memory.total,memory.free --format=csv
python -c "import torch; print(torch.__version__, torch.cuda.is_available(), torch.version.cuda)"
```

Do not substitute quantization or unverified CPU offload. Once a suitable GPU is available, run the official Qwen 8B reference with the fixed revision and record peak VRAM. The canonical input path and MRL post-processing contract are now recorded above; the official processor's video path also emitted a `cap_pixels_per_frame` warning in the CPU probe, so video pixel-budget parity remains to be verified. Safe backend implementation can proceed, but do not claim 8B CUDA/BF16 parity or v0.7.0 release readiness until the required GPU gate passes.
